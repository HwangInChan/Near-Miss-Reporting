# 아차사고(Near-miss) & 인적 오류 리포팅 웹앱 — 프로토타입

현장 작업자가 아차사고를 3초 만에 보고하고, 안전 관리자가 인적 오류를 태깅해
하인리히 1:29:300 법칙 기반으로 중대재해를 예측/예방하는 프로토타입입니다.

## 버전 히스토리 (요약)

- **v0.1**: 정적 더미데이터 기반 프로토타입 (작업자 화면 / 관리자 대시보드 뼈대)
- **v0.2**: SQLite DB 연동 — 작업자 화면 제출이 실제로 대시보드에 반영됨, 조치완료 번복 기능
- **v0.3**:
  - 마이크 버튼이 **실제 브라우저 음성 인식**(Web Speech API)으로 동작 (더 이상 정해진 문장을
    무작위로 보여주는 모사 기능이 아님)
  - 인적 오류 분류값을 영어(Slip/Lapse/Mistake/Violation)에서 **한글(실수/망각/착오/위반)로 통일**
    — 화면 표시용 라벨이 아니라 DB에 실제로 저장되는 값 자체를 한글로 바꿈
  - 관리자 대시보드 진입 시 리포트가 자동으로 선택되어 상세 패널이 열리던 것을 제거 (사용자가
    직접 클릭하기 전까지는 빈 상태 유지)
  - 대시보드 분석 위젯 4종(임계점 경보·하인리히 피라미드·인적오류 도넛·구역별 히트맵)을
    한 줄에 배치하고, 창 너비에 따라 자동으로 2열/1열로 줄바꿈되는 반응형 레이아웃으로 개편
  - 하인리히 피라미드를 사다리꼴 3단이 아닌, 꼭짓점이 있는 진짜 삼각형 하나로 재작성
- **v0.4**:
  - 음성 인식 관련 이슈 원인 확정: 개발 중 한때 특정 PC에서 음성 인식이 계속 실패했는데,
    여러 차례 코드를 점검/재설계(중복 세션 방지, 매번 새 인스턴스 생성 등)한 끝에도 재현되어
    네트워크 차단을 의심했으나, 다른 기기(모바일)로 배포본에 접속해 테스트한 결과 정상
    동작을 확인했다. 최종적으로 **문제가 있던 특정 노트북의 마이크 하드웨어 자체의 문제**로
    결론지었다 — 코드/네트워크 문제가 아니었다. 참고로 이 과정에서 발견해 고친 진짜 코드
    버그(React Strict Mode로 인한 중복 세션 생성, `stop()` 호출 시 상태를 실제보다 먼저
    갱신하던 문제 등)는 그대로 반영되어 있으며, 이후로도 유효한 개선 사항이다.
  - 모바일 화면에서 대시보드 헤더의 "새로고침" 버튼 글자가 좁은 화면 폭 때문에 단어 중간에서
    줄바꿈되던 문제 수정 (헤더를 모바일에서는 세로로, 데스크탑에서는 가로로 배치하는 반응형
    구조로 변경하고, 버튼/카운트 텍스트에 줄바꿈 방지 처리 추가)
- **v0.5**:
  - **수기 입력 복원**: 신고 내용 입력칸이 항상 표시되고 항상 타이핑 가능해졌다. 이전에는
    (1) 음성 인식을 지원하는 브라우저에서는 마이크를 한 번 눌러야만 입력칸이 나타났고,
    (2) 녹음 중에는 `readOnly` 상태라 타이핑이 막혀 있었다. 그 결과 마이크가 고장난 PC처럼
    "브라우저는 음성 인식을 지원하지만 실제로 인식은 안 되는" 환경에서 신고를 아예 할 수
    없었다. 이제 마이크와 키보드 중 아무거나 쓸 수 있다.
  - 음성 인식 결과가 기존에 타이핑해둔 내용을 덮어쓰지 않고 **뒤에 이어붙도록** 변경.
    녹음 중 실시간 인식 미리보기도 입력칸 본문이 아니라 그 아래 별도 영역에 표시해서,
    사용자가 입력 중인 내용이 지워지지 않는다.
- **v0.6**: **사번 기반 신고자 식별 + 포상 집계 제도** 도입
  - 작업자가 이 기기에서 처음 신고할 때 **사번 + 이름을 한 번 등록**하면, 이후에는
    브라우저에 기억되어 다시 묻지 않는다 (공용 기기라면 상단 바의 "변경"으로 전환).
  - **개별 신고마다 익명 선택 가능.** 익명으로 내면 사번이 아예 저장되지 않으며,
    그 대가로 포상 집계에서 제외된다는 점을 체크 시점에 화면에 명시한다.
  - **내 신고 이력 화면**(`/my-reports`) 추가 — 본인이 낸 기명 신고와 그 처리 상태,
    누적/조치완료/우수 신고 건수를 확인할 수 있다.
  - 관리자 대시보드에 **포상 집계 순위표** 추가. 상세 패널에서 **"우수 신고" 지정** 가능.
  - `workers` 테이블 신설 및 `reports`에 `employee_id`/`is_anonymous`/`is_exemplary`
    컬럼 추가. 기존에 쓰던 DB 파일도 앱 실행 시 **자동으로 마이그레이션**되므로
    지우지 않고 그대로 쓸 수 있다.
- **v0.7**:
  - **임계점 기준을 150건 → 50건으로 조정**하고, 이 값이 학술적 기준이 아니라 조직이
    스스로 정하는 관리 기준임을 코드 주석과 문서에 명시했다. 시드 데이터도 90건 →
    23건으로 줄여 임계점까지 여유를 두었다.
  - 임계점 경보 위젯에 **"임계점 도달 예상" 유닛 추가**. 최근 2주간의 하루 평균 발생률로
    남은 건수를 나눠 며칠 뒤 임계점에 닿을지 추정해 보여준다 (`forecastThresholdArrival`).
    "지금 몇 건인가"에 더해 "이 추세면 언제 터지는가"를 함께 제시하기 위한 지표다.
  - 인적 오류 도넛 차트와 범례 크기를 키워 카드 우측 여백을 줄였다.
- **v0.8**: **배포 빌드 실패(SQLITE_BUSY) 수정**
  - 증상: Render 배포 중 `Failed to collect page data for /api/workers`와 함께
    `SQLITE_BUSY`로 빌드가 실패했다.
  - 원인: `lib/db.ts`가 **모듈을 import하는 시점에** 곧바로 DB 파일을 열도록 되어 있었다.
    Next.js는 빌드 시 여러 워커 프로세스를 병렬로 띄워 각 API 라우트를 로드하는데,
    `/api/reports`·`/api/workers`·`/api/rankings`가 동시에 같은 SQLite 파일을 열고
    `PRAGMA`/`ALTER TABLE`을 실행하다 잠금 충돌이 났다. 로컬 빌드에서는 타이밍이
    우연히 겹치지 않아 통과했던 것이다.
  - 수정: DB 커넥션을 **지연 초기화**로 바꿨다(`getDb()`). 이제 모듈을 불러오는 것만으로는
    DB 파일이 열리지 않고, 실제로 쿼리를 실행하는 첫 시점에만 열린다. 빌드 중에는
    DB 파일이 아예 생성되지 않는다. 보조 안전장치로 `busy_timeout = 5000`도 설정해,
    잠금이 걸려도 즉시 실패하지 않고 최대 5초까지 기다리게 했다.
- **v0.9**: **100% 배율 기준 레이아웃 정리**
  - 전역 CSS에 `word-break: keep-all` 적용. 한글은 브라우저 기본값에서 단어 중간이
    아무 데서나 끊기는데("표시됩 / 니다", "기 / 준 추정"), 이제 어절 단위로만
    줄바꿈된다. 개별 문구를 손보는 대신 원인을 한 곳에서 해결한 것이다.
  - 4열 배치 시 카드 폭이 좁아지는 것을 감안해 위젯 크기를 재조정했다: 도넛 차트 축소,
    범례 폰트 축소, 임계점 위젯 아이콘·패딩 축소, 히트맵 셀 높이 축소, 카드 제목/부제
    크기 하향.
  - 하인리히 하단 설명문과 임계점 도달 예측 문구를 짧게 다듬어 좁은 폭에서도 자연스럽게
    두 줄 안에 들어오도록 했다.
- **v0.10**: **다국어 지원 (한국어 / English / Tiếng Việt)**
  - 작업자용 화면 전체를 3개 언어로 번역했다. 선택한 언어는 브라우저에 기억된다.
  - **음성 인식 언어도 함께 전환된다** (`ko-KR` / `en-US` / `vi-VN`). 영어·베트남어로
    말해도 그대로 받아적힌다.
  - 공장 구역명도 언어별로 번역했다. 외국인 작업자가 자기 위치를 정확히 고를 수 있어야
    신고 데이터의 품질이 유지되기 때문이다.
  - 관리자 대시보드는 한국어를 유지했다 (사유는 아래 "다국어 지원" 섹션 참고).
- **v0.11**: **기능적 공백 세 가지 보완**
  - **심각도 수정 기능 추가.** 그동안 새로 접수되는 신고는 전부 `medium`(주의)으로
    저장됐고 관리자가 이를 바꿀 방법이 없었다. 즉 실제 운영 데이터의 심각도가
    전부 동일해져 히트맵·통계가 무의미해지는 결함이었다. 상세 패널에서 경미/주의/위험을
    선택할 수 있게 했다.
  - **사진 실제 업로드 구현.** 이전에는 파일을 고르기만 하고 `photoAttached: true`라는
    불리언만 전송돼, 관리자 화면에 "사진 첨부됨"이라 뜨지만 볼 수 없었다(표시가
    사실과 달랐다). 이제 이미지를 실제로 저장하고 상세 패널에서 조회할 수 있다.
  - **배후 요인 순위 차트 추가.** 관리자가 조도 부족·피로 누적 등을 태깅해도 그것을
    모아 보는 화면이 없어 태깅의 목적(구조적 결함 발견)이 달성되지 않았다.
    집계 함수는 이미 있었으나 어디서도 쓰이지 않는 죽은 코드 상태였다.
- **v0.12**: **DB를 libSQL로 전환 — 배포 환경에서도 데이터 영구 보존**
  - `better-sqlite3` → `@libsql/client`로 교체. **코드 한 벌로 로컬 파일과 원격
    Turso DB를 모두 지원**한다(환경변수로 전환). 로컬 개발은 Turso 계정 없이 그대로 된다.
  - 원격 DB 클라이언트는 비동기이므로 `lib/reportRepository.ts`의 모든 함수와
    이를 호출하는 API 라우트를 `async/await`로 전환했다.
  - **대시보드 폴링을 8초 → 30초로 늘리고, 탭이 보일 때만 폴링**하도록 했다.
    Turso는 "스캔한 행 수"로 사용량을 계산하는데, 기존 설정으로는 신고가
    1,000건만 쌓여도 무료 한도의 194%를 소모하는 것으로 계산됐다(아래 참고).
    개선 후 같은 조건에서 17%로 내려간다.
- **v0.13**: **포상 집계 누락 버그 수정 + 사이트 제목 변경**
  - 증상: 배포본에서 신고를 접수해도 포상 집계에 반영되지 않았다.
  - 원인: 작업자 신원은 브라우저 `localStorage`에도 저장되는데, DB를 새로 만들거나
    옮기면(예: 로컬 파일 → Turso) **브라우저에는 사번이 남아 있지만 서버 `workers`
    테이블에는 없는** 상태가 된다. 기존 집계 쿼리가 `workers` 기준 INNER JOIN이라
    이런 신고가 통째로 누락됐다. 같은 이유로 신고자 표시도 이름 대신 "현장 작업자"로
    저장됐다.
  - 수정 1: 신고 시 **사번과 이름을 함께 전송**해, 서버에 해당 사번이 없으면 자동으로
    등록한다(자가 복구). 앞으로 DB를 옮겨도 같은 문제가 재발하지 않는다.
  - 수정 2: 집계 쿼리를 **reports 기준 LEFT JOIN**으로 바꿨다. 작업자 등록이 어긋나도
    사번으로는 집계되고 이름만 `(미등록 사번)`으로 표시되므로, 데이터가 조용히
    사라지지 않는다.
  - 브라우저 탭 제목을 "아차사고 리포팅 | Safety Command Center" →
    **"아차사고 신고 서비스"**로 변경.
- **v0.14**: **관리자 대시보드 접근 제어 + 모바일 레이아웃 수정**
  - 대시보드 진입 시 관리자 암호를 요구한다. 작업자 화면(신고·내 이력)은 암호 없이
    그대로 이용할 수 있다.
  - 인증 상태는 `sessionStorage`에 저장해 **탭을 닫으면 자동으로 다시 잠긴다**.
    공용 PC를 염두에 둔 선택이다.
  - 랜딩 화면의 언어 전환 버튼이 `absolute`로 떠 있어 좁은 화면에서 제목 위에
    겹쳐 글자가 잘리던 문제를 수정했다(일반 흐름으로 배치).
- **v1.0**: **위험성평가 기반 개선 우선순위 도출**
  이전까지 이 앱은 "무슨 일이 있었는지 보여주는" 서술적(descriptive) 도구였다.
  차트를 아무리 늘려도 "그래서 무엇을 먼저 해야 하는가"는 관리자가 머릿속으로
  종합해야 했다. v1.0에서 **처방적(prescriptive) 도구로 전환**한다.
  - 산업안전보건법상 위험성평가 방법론(위험성 = 가능성 × 중대성)을 적용해
    구역별 위험성 점수를 자동 산출하고 3×3 매트릭스에 배치한다.
  - 위험성 순으로 정렬한 **개선 우선순위 목록**과, 각 구역의 지배적 배후 요인에서
    도출한 **권고 개선대책**을 제시한다. 대책은 Hierarchy of Controls
    (본질적 → 공학적 → 관리적 → 보호구) 순으로 정렬된다.
  - 인적 오류 유형별로 대책 접근 방향 조언을 덧붙인다.
  - 추가 DB 조회 없이 이미 불러온 리포트로 계산하므로 Turso 행 읽기 사용량이
    늘지 않는다.
  - (레이아웃) 위험성 매트릭스와 개선 우선순위 카드는 아래 끝을 맞추되 픽셀 높이를
    고정하지 않는다. 오른쪽 목록에 `min-h-0`을 주어 "필요한 높이"를 주장하지 않게
    하면, 행 높이는 왼쪽 매트릭스가 결정하고 목록은 남는 높이 안에서 스크롤된다.

## DB는 어떻게 되어 있나요?

### 로컬과 배포가 같은 코드로 동작합니다

DB 접근은 `@libsql/client` 하나로 통일되어 있고, **환경변수만으로 대상이 바뀝니다.**

| 환경 | 설정 | 대상 |
| --- | --- | --- |
| 로컬 개발 | 아무것도 설정하지 않음 | `data/near-miss.db` 파일 |
| 배포 | `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` | Turso 원격 DB |

즉 로컬에서는 Turso 계정 없이 지금까지처럼 작업하고, 배포할 때만 Render의
Environment 탭에 두 변수를 넣으면 됩니다. 코드는 건드리지 않습니다.
`.env.example`에 설정 방법이 정리되어 있습니다.

### Turso 무료 한도와 이 앱의 사용량

무료 플랜은 저장 5GB, 월 5억 행 읽기, 1천만 행 쓰기입니다.

**저장 용량은 제약이 아닙니다.** 사진을 압축해 평균 200KB로 저장하므로 5GB면
약 26,000장이 들어갑니다. 신고 10,000건에 절반이 사진 첨부여도 약 986MB(19%)입니다.
그래서 사진을 외부 스토리지로 분리하지 않고 DB 안에 함께 둡니다.

**실제 제약은 "행 읽기"입니다.** Turso는 요청 수가 아니라 쿼리가 스캔한 행 수로
사용량을 계산합니다. 대시보드 폴링 1회마다 리포트 전체가 여러 번 스캔되므로
(목록 + 포상 집계 JOIN + 배후요인 통계), 폴링 주기가 사용량을 좌우합니다.

| 조건 | 8초 폴링(기존) | 30초 + 탭 보일 때만(현재) |
| --- | --- | --- |
| 신고 500건, 하루 8시간 사용 | 162M행 (32%) | 43M행 (9%) |
| 신고 1,000건, 하루 8시간 | 324M행 (65%) | 86M행 (17%) |
| 신고 1,000건, 24시간 켜둠 | 972M행 (**194% 초과**) | 259M행 (52%) |

즉시 최신 상태를 보려면 헤더의 "새로고침" 버튼을 쓰면 됩니다.

- **엔진**: libSQL (SQLite 호환). 로컬에서는 파일 기반이라 별도 DB 서버 설치가 필요 없습니다.
- **파일 위치**: `data/near-miss.db` (첫 실행 시 자동 생성, `.gitignore`에 포함되어 저장소에는 올라가지 않습니다)
- **직접 관리하는 방법**: 무료 GUI 툴인 [DB Browser for SQLite](https://sqlitebrowser.org)로
  `data/near-miss.db` 파일을 열면, 엑셀처럼 테이블을 보고 행을 직접 추가/수정/삭제할 수 있습니다.
  서버를 끄고 켜도 데이터는 그대로 유지됩니다.
- **DB 파일 경로를 바꾸고 싶다면**: 환경변수 `DB_FILE_PATH`를 지정하세요.
  (`DB_FILE_PATH=/some/path/near-miss.db npm run dev`)

### 테이블 구조

- **reports** — 아차사고 신고. 신고자 사번(`employee_id`), 익명 여부(`is_anonymous`),
  우수 신고 지정 여부(`is_exemplary`) 포함.
- **workers** — 등록된 작업자 (사번, 이름, 등록일).

### 스키마 자동 마이그레이션

이전 버전에서 쓰던 DB 파일이 있어도 지울 필요가 없습니다. 앱을 실행하면 `lib/db.ts`의
`migrate()`가 현재 컬럼 목록을 확인해 없는 컬럼만 `ALTER TABLE`로 추가합니다. 사번 도입
이전에 쌓인 과거 신고는 `employee_id`가 비어 있어 포상 집계에는 잡히지 않고, 그 외에는
정상적으로 조회됩니다.

### 데이터 초기화하기

```bash
npm run db:seed         # DB가 비어있을 때만 작업자 7명 + 리포트 23건 시드
npm run db:seed:force   # 기존 데이터를 모두 지우고 새로 시드
```

## 인적 오류 분류값은 한글입니다

`lib/types.ts`의 `HumanErrorType`은 `"실수" | "망각" | "착오" | "위반"` 네 가지 값입니다.
이건 화면에만 보이는 라벨이 아니라 **DB `reports.human_error_type` 컬럼에 실제로 저장되는 값**이고,
`lib/constants.ts`의 `HUMAN_ERROR_COLORS`(도넛 차트·태깅 버튼 색상 매핑)도 이 값을 그대로 키로
씁니다. 나중에 이 분류 체계를 바꾸고 싶다면 `lib/types.ts` → `lib/constants.ts` →
`lib/dummyData.ts`(시드용 로컬 배열) → `lib/utils.ts`(`countByHumanError`) 순서로 확인하면
빠짐없이 찾을 수 있습니다.

## 신고 포상 제도 (사번 기반)

안전문화 실천 방안으로 아차사고 신고제도를 도입하고, 신고 건수를 집계해 포상에
반영하는 것을 전제로 설계했습니다.

### 신고자 식별

- 작업자가 이 기기에서 처음 신고할 때 **사번 + 이름**을 한 번 등록합니다. 등록 정보는
  브라우저 `localStorage`에 저장되어 이후에는 다시 묻지 않습니다 (`lib/utils.ts`의
  `loadStoredWorker` / `saveStoredWorker`). 공용 태블릿이라면 신고 화면 상단 바의
  "변경"을 눌러 다른 사람으로 전환할 수 있습니다.
- 서버에는 `workers` 테이블에 사번·이름이 저장되고, 각 신고(`reports.employee_id`)가
  이를 참조합니다.

### 익명 신고와 포상의 트레이드오프

아차사고 신고에는 성격이 다른 것들이 섞여 있습니다. "바닥에 기름이 흘렀다"(환경 신고)는
신고자에게 아무 위험이 없지만, "제가 프레스에 손이 들어갈 뻔했다"(자기 실수 신고)는
정작 가장 값진 데이터임에도 불이익을 우려해 숨기기 쉽습니다. 여기에 기명 포상만
강제하면 **안전한 신고만 골라서 하고 정작 중요한 자기 실수는 감추는** 부작용이 생깁니다.

그래서 이 앱은 다음과 같이 설계했습니다.

- 기본은 **기명 신고** → 자동으로 포상 집계에 반영됩니다.
- 신고 건별로 **"이번 건은 익명으로" 옵션**을 선택할 수 있습니다. 익명을 선택하면
  사번이 아예 저장되지 않고(역추적 불가), 그 대가로 **포상 집계에서 제외**됩니다.
- 이 트레이드오프를 체크하는 시점에 화면에 명시해서, 작업자가 알고 선택하게 합니다.

구현상 익명 신고는 `employee_id`가 NULL이므로, 포상 집계 쿼리(`workers JOIN reports`)에서
**별도 예외 처리 없이 구조적으로 제외**됩니다 (`lib/reportRepository.ts`의
`getRewardRankings()`).

### 건수 포상만으로는 부족한 이유

단순 건수 순위로만 포상하면 저품질 신고가 급증합니다. 그래서 관리자가 상세 패널에서
**"우수 신고"로 지정**할 수 있게 하고(`is_exemplary`), 순위표 정렬을
**우수 신고 수 → 총 신고 수** 순으로 두어 질적으로 좋은 신고가 상위에 오도록 했습니다.

### 첨부 사진은 어떻게 저장되나

사진은 **SQLite BLOB으로 DB 파일 안에** 함께 저장됩니다(`report_photos` 테이블).
파일시스템에 따로 두지 않은 이유는, 이 앱이 "DB가 파일 하나로 완결되는" 구조이고
Render 무료 플랜처럼 컨테이너 재시작 시 파일시스템이 초기화되는 환경에서
"DB 기록은 남았는데 이미지만 사라지는" 불일치가 생기는 것보다 둘의 수명을
일치시키는 편이 낫기 때문입니다. 백업도 DB 파일 하나만 복사하면 됩니다.

- `report_photos`는 `reports`와 1:1이지만 **일부러 별도 테이블로 분리**했습니다.
  같은 테이블에 두면 목록을 조회할 때마다 수십 건의 이미지 바이트가 메모리에
  딸려옵니다. 사진은 상세 화면에서 한 건씩만 필요합니다.
- 업로드 전 **클라이언트에서 리사이즈·압축**합니다(긴 변 1280px, JPEG 품질 0.7 →
  보통 150~300KB). 요즘 폰 사진은 원본이 3~8MB라 그대로 넣으면 DB가 급격히 커지고
  현장의 느린 네트워크에서 업로드도 오래 걸립니다.
- 서버에서도 **1.5MB 상한과 형식(jpeg/png/webp)을 검증**합니다. 클라이언트 압축을
  신뢰하지 않고 서버에서 한 번 더 막습니다.

### 임계점 경보 기준값에 대하여

`lib/constants.ts`의 `NEAR_MISS_ALERT_THRESHOLD`(현재 50)는 **학술적으로 확립된 수치가
아니라 조직이 스스로 정하는 관리 기준**입니다. 하인리히 비율에서 아차사고는 300이지만,
300건이 쌓일 때까지 방치했다가 경보를 울리는 것은 예방이라는 목적에 맞지 않으므로
훨씬 이른 시점을 임계점으로 잡았습니다. 실제 도입 시에는 사업장 규모·근로자 수·과거
재해 이력을 반영해 조정해야 합니다.

경보 위젯은 두 가지를 함께 보여줍니다.

1. **현재 누적 건수와 진행률** — 80% 도달 시 노란색(임계점 근접), 100%에서 빨간색으로 점등.
2. **임계점 도달 예상** — 최근 2주간 하루 평균 발생률로 남은 건수를 나눈 단순 선형 외삽.
   정밀 예측이 아니라 "이 추세면 언제쯤"이라는 경보용 지표입니다. 최근 신고가 너무 적어
   추정이 무의미할 때는 "산출 불가"로 표시합니다.

### 신고자 피드백 루프

작업자는 `/my-reports`에서 본인이 낸 기명 신고와 그 처리 상태(미분류/분석중/조치완료),
누적·조치완료·우수 신고 건수를 볼 수 있습니다. "내 신고가 실제로 뭔가를 바꿨다"는
체감이 다음 신고로 이어지도록 하기 위한 화면입니다.

## 음성 인식

작업자 화면의 마이크 버튼은 브라우저 내장 **Web Speech API**를 사용합니다
(`lib/useSpeechRecognition.ts`). 별도 API 키나 서버 비용 없이, 실제로 말한 내용이
한국어로 인식되어 텍스트 칸에 채워집니다.

**음성 인식은 어디까지나 보조 수단이며, 신고 내용은 언제든 키보드로 직접 입력할 수 있습니다.**
입력칸은 화면에 항상 표시되고 녹음 중에도 타이핑이 가능합니다. 마이크가 없거나 고장난 기기,
음성 인식을 지원하지 않는 브라우저에서도 신고 자체는 문제없이 됩니다.

- **한 문장 단위로 동작**(`continuous: false`): 마이크를 누르면 듣기 시작하고, 한 문장을
  말하면(또는 침묵이 감지되면) 자동으로 종료됩니다. "3초 보고"라는 용도에 맞춘 설정입니다.
- **마이크를 누를 때마다 완전히 새 인식 세션을 만듭니다**: 이전 세션 상태를 재사용/추적하지
  않고, 매번 기존 것을 폐기(`abort`)하고 새로 생성합니다. 이렇게 한 이유는 브라우저의
  `InvalidStateError`("recognition has already started")가 상태 추적 방식으로는 계속
  재현되어, 아예 추적할 상태 자체를 없애는 방향으로 설계를 바꿨기 때문입니다.
- **지원 브라우저**: Chrome, Edge (Chromium 계열). Firefox·Safari는 지원하지 않으며,
  이 경우 자동으로 "이 브라우저는 음성 인식을 지원하지 않아요" 안내가 뜨고 직접 입력
  칸으로 전환됩니다.
- **HTTPS 필요**: 브라우저 보안 정책상 `localhost` 또는 HTTPS 환경에서만 동작합니다.
  Render에 배포하면 자동으로 HTTPS가 적용되므로 문제없습니다.
- **마이크 권한**: 처음 사용할 때 브라우저가 마이크 권한을 물어봅니다. 거부하면
  화면에 안내 메시지가 뜹니다.

### ⚠️ 음성 인식이 안 될 때 확인해야 할 것들

Chrome의 음성 인식은 마이크 입력을 **구글 서버로 전송해서 처리한 뒤 결과를 돌려받는**
방식으로 동작합니다. 개발 중 특정 PC에서 "듣고 있어요" 상태까지는 되는데 인식 결과가
끝내 오지 않는 문제를 겪었고, 처음에는 학교 네트워크가 구글 음성 인식 서버 접근을 막고
있는 것으로 의심했습니다. 하지만 같은 배포본에 다른 기기(모바일)로 접속해 테스트해보니
정상 동작했고, 최종적으로는 **그 PC의 마이크 하드웨어 자체의 문제**로 확인됐습니다 —
코드나 네트워크 문제가 아니었습니다.

그래도 아래 두 가지는 여전히 이 기능이 안 될 수 있는 일반적인 원인이니 순서대로 확인하세요.

1. **마이크 하드웨어/OS 설정 확인**: OS의 소리 설정에서 마이크가 실제로 소리를 인식하는지
   확인하거나(다른 앱에서 마이크 테스트), 다른 기기(휴대폰 등)로 같은 페이지에 접속해
   같은 증상이 재현되는지 봅니다. 다른 기기에서는 되는데 특정 PC에서만 안 된다면 그 PC의
   마이크/드라이버 문제일 가능성이 큽니다.
2. **네트워크 차단 확인**: 마이크는 정상인데도 안 된다면, 개발자 도구 콘솔에
   `[useSpeechRecognition] onerror: network`가 찍히는지 확인하세요. 이게 찍히면 학교·회사
   네트워크의 방화벽/프록시가 구글 음성 인식 서버 접근을 막고 있다는 뜻이며, 코드로 해결할
   수 있는 부분이 아닙니다. 휴대폰 모바일 데이터로 전환해 같은 테스트를 해보면 확인됩니다.

**확인 방법**: 마이크를 누르고 몇 초 기다렸을 때 뜨는 안내 메시지를 확인하세요.
"네트워크 문제로 음성 인식 서버에 연결하지 못했습니다"가 뜨거나, 개발자 도구 콘솔에
`[useSpeechRecognition] onerror: network`가 찍히면 네트워크 차단이 원인입니다.
휴대폰 핫스팟 등 다른 네트워크로 바꿔서 같은 테스트를 해보면 확실히 확인할 수 있습니다.

### 이미지 인식(사진 속 내용 자동 분석)은 왜 지금 안 넣었나

사진을 실제로 "이해"하려면 Google Cloud Vision, 네이버 Clova OCR, OpenAI Vision API
같은 유료 클라우드 서비스가 필요하고, 이는 **본인 명의로 가입 후 API 키를 발급받아야만**
사용할 수 있습니다. 코드만으로 해결할 수 있는 부분이 아니라 이번에는 넣지 않았습니다.
나중에 API 키를 발급받으시면, `components/report/PhotoUploader.tsx`에서 사진을
업로드하는 지점에 해당 API 호출을 추가하는 방식으로 붙일 수 있습니다.

## 위험성평가 기반 개선 우선순위 (v1.0 핵심 기능)

### 왜 필요한가

기존 대시보드는 히트맵·도넛·순위 차트로 **현상을 보여주기만** 했다. 문제는
관리자가 그 화면들을 눈으로 훑고 "그래서 어디부터 손대야 하나"를 스스로 판단해야
한다는 점이다. 특히 히트맵은 **건수만 세기 때문에 경미 사고 10건과 위험 사고 10건이
똑같이 빨갛게** 보인다. 실제로 먼저 손봐야 할 곳을 놓치기 쉬운 구조다.

### 방법론: 위험성 = 가능성 × 중대성

산업안전보건법 제36조와 KOSHA 위험성평가 지침의 기본 구조를 따른다.
3×3 매트릭스를 사용해 위험성 점수를 1~9로 산출한다(곱의 특성상 5·7·8은 나오지 않는다).

| 위험성 점수 | 등급 | 조치 |
| --- | --- | --- |
| 6 ~ 9 | 높음 | 즉시 개선 (작업 중지 검토) |
| 3 ~ 4 | 보통 | 개선 계획 수립 필요 |
| 1 ~ 2 | 낮음 | 현 수준 유지·관리 |

**이 앱의 차별점은 가능성과 중대성을 평가자의 주관적 추정이 아니라 실제 접수된
아차사고 데이터에서 산출한다는 것이다.** 전통적 위험성평가는 담당자의 경험에
의존해 평가자마다 결과가 달라진다는 한계가 지적되어 왔다.

#### 가능성(빈도) 산출

해당 구역의 신고 건수를 전체 구역 평균과 비교해 3단계로 환산한다. 절대 건수 기준을
쓰면 사업장 규모·운영 기간에 따라 의미가 달라지므로 상대 기준을 택했다.

다만 상대 기준만 쓰면 데이터가 적을 때 불안정하다. 전체 신고가 1건뿐이면 그 1건이
평균의 9배가 되어 "빈번"으로 판정된다. 아차사고 1건으로 반복성을 주장할 수는 없으므로
**절대 최소 건수 조건**을 함께 건다(기본값: 상=3건, 중=2건).

두 조건의 성격이 다르다는 점에 유의해야 한다.

| 조건 | 성격 | 사업장 규모 대응 |
| --- | --- | --- |
| 평균 대비 (2배 / 1배) | 상대 기준 | 자동으로 적응 |
| 최소 건수 | 절대 기준 | **자동 적응 안 됨 → 설정 필요** |

그래서 최소 건수는 **사업장별 설정값**으로 분리했다(v1.5). 아래 "평가 기준값 설정" 참고.

#### 중대성(강도) 산출 — 평균이 아니라 최댓값

해당 구역에서 **관측된 최대 심각도**를 사용한다. 이것이 방법론적으로 중요한 지점이다.
위험성평가는 "예상되는 최악의 결과(worst credible outcome)"로 중대성을 판단한다.
평균을 쓰면 경미 사고 다수에 묻혀 중대재해 가능성이 희석되기 때문이다.

실제로 시드 데이터에서 A동 프레스 라인은 신고가 2건뿐이라 히트맵에서는 눈에 띄지
않지만, 그중 "위험" 등급이 있어 개선 우선순위 4위로 올라온다. 건수만 세는 방식으로는
발견할 수 없는 구역이다.

### 배후 요인 설계

배후 요인은 Reason의 스위스 치즈 모델에서 말하는 **잠재 조건(latent condition)**에
해당한다. 설계에서 가장 중요한 원칙은 **불안전한 행동이 아니라 그 행동을 유발한
조건을 담아야 한다**는 것이다.

v1.2에서 다음과 같이 재설계했다.

| 변경 | 내용 | 이유 |
| --- | --- | --- |
| 제거·수정 | 보호구 미착용 → **보호구 미지급·불편** | "미착용"은 배후 요인이 아니라 불안전한 행동이다. 그 자체가 설명을 필요로 하며(왜 착용하지 않았나), 인적 오류 유형 "위반"과도 중복된다 |
| 수정 | 작업 절차 미숙지 → **작업 절차 미비·불명확** | "미숙지"는 개인을 탓하는 프레임이다. 잠재 조건은 조직의 실패를 가리켜야 하므로 절차 자체의 결함을 묻도록 바꿨다 |
| 추가 | **설비·방호장치 결함** | 가장 큰 공백이었다. 난간 고정핀 풀림, 비상정지줄 위치 부적절, 프레스 방호 미비, 계단 손잡이 등 설비 결함 사례가 다수인데 해당 항목이 없었다. 공학적 대책으로 직결되는 가장 근본적인 개선 대상이다 |
| 추가 | **의사소통·신호 미흡** | 지게차 후진 경보 미인지 등 신호 전달 실패 유형 |
| 추가 | **환기·유해물질** | 도장 부스 어지러움 등 작업환경 유해요인 |
| 통합 | 정리정돈 불량 → **정리정돈·바닥 상태 불량** | 누유로 인한 미끄러짐까지 포괄 |

기본 목록에 없는 요인은 **직접 입력**할 수 있다. 목록을 고정하면 관리자가 실제와
다른 항목에 억지로 끼워 맞추게 되고, 그렇게 쌓인 집계는 오히려 판단을 흐린다.
직접 입력한 요인은 표준 대책 매핑이 없으므로 권고 대책에는 나타나지 않지만,
배후 요인 순위 집계에는 정상적으로 반영된다.

### 평가 기준값 설정 (사업장별 조정)

**위험성평가의 판정 경계는 표준으로 정해진 수치가 아니다.** KOSHA 위험성평가 지침도
"빈도를 3단계로 나누라"까지만 규정하고, 그 경계를 어디에 그을지는 사업장 재량으로 둔다.
따라서 다음 값들은 코드 상수가 아니라 **관리자 대시보드에서 조정하는 설정값**이다.

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| 임계점 경보 기준 | 50건 | 누적 아차사고가 이 건수에 도달하면 경보 점등 |
| 가능성 '상' 최소 건수 | 3건 | 구역별 신고가 이 이상이어야 가능성 3점(빈번) |
| 가능성 '중' 최소 건수 | 2건 | 구역별 신고가 이 이상이어야 가능성 2점(가끔) |

#### 왜 규모별로 달라야 하는가

최소 건수는 절대 기준이라 사업장 규모에 자동으로 적응하지 않는다.

- **소규모(50인 미만)** — 신고 자체가 적으므로 2~3건도 유의미한 반복 신호다.
- **대규모(300인 이상)** — 3건은 노이즈에 가깝다. 10건 이상은 되어야 "반복된다"고
  말할 수 있다.
- **고위험 업종(건설·화학)** — 같은 규모라도 기준을 낮춰 민감하게 잡을 필요가 있다.

화면에서 규모별 권장값(소/중/대규모) 프리셋을 제공하되, 이는 참고값일 뿐이다.

#### 실제 도입 시 권장 절차

1. 과거 1~2년 자기 사업장 데이터로 구역별 신고 건수 분포를 확인한다.
2. 그 분포를 근거로 경계를 정하고, **산업안전보건위원회 심의**를 거쳐 확정한다.
3. 운영하면서 "너무 많이 걸린다 / 전혀 안 걸린다" 싶으면 조정한다.

한 번 정하고 끝나는 값이 아니라 운영하며 다듬는 값이다.

#### 유효성 검증

저장 시 서버에서 검사한다. 특히 **`'상' 최소 건수 < '중' 최소 건수`인 조합을 막는다.**
이 경우 등급 판정이 역전되어 평가 자체가 무의미해지기 때문이다.
설정은 `settings` 테이블에 저장되므로 서버를 재시작해도 유지된다.

### 개선대책 도출: Hierarchy of Controls

각 구역의 지배적 배후 요인에서 표준 대책을 도출하되, **위험성 감소대책의 우선순위**에
따라 정렬한다.

| 단계 | 성격 | 예시 |
| --- | --- | --- |
| 본질적 | 위험원 자체를 제거·대체 | 저소음 설비로 교체, 야간 고위험 작업을 주간으로 이동 |
| 공학적 | 설비·환경으로 차단 | 방음 커버 설치, 국소조명 증설, 통로 구획선 |
| 관리적 | 절차·교육·감독 | 작업표준 재교육, 점검 체크리스트, 교대 스케줄 조정 |
| 보호구 | 개인 착용 장비 | 청력보호구 지급 |

**개인보호구는 항상 최후의 수단이다.** 실무에서 흔한 오류가 관리적 대책과 보호구에만
의존하는 것인데, 이는 위험원을 그대로 둔 채 사람에게 부담을 전가하는 방식이다.
이 앱은 근본적인 대책을 목록 상단에 배치해 그 순서를 상기시킨다.

### 인적 오류 유형과 대책의 연결

Reason의 분류(실수/망각/착오/위반)에서 나오는 중요한 시사점은 **"실수는 교육으로 막을
수 없다"**는 것이다. 유형별로 대책의 성격이 달라야 한다.

- **실수(Slip)** — 주의력에 의존한 교육은 효과가 없다. 잘못된 동작이 애초에 불가능하도록
  공학적 방호(인터록, 방호덮개)를 우선한다.
- **망각(Lapse)** — 절차를 기억에 의존시키지 않는다. 체크리스트·시각적 표시·강제 확인
  단계를 공정에 삽입한다.
- **착오(Mistake)** — 판단 자체가 틀린 경우이므로 작업표준의 명확성과 교육 내용을 본다.
- **위반(Violation)** — 몰라서가 아니라 지키기 어려운 여건일 가능성이 크다. 처벌보다
  왜 우회하게 되는지(시간 압박, 불편한 보호구)를 먼저 파악한다.

대시보드는 각 구역의 지배적 오류 유형을 판별해 이 조언을 함께 표시한다.

### 개선계획서 출력

대시보드 헤더의 "개선계획서" 버튼을 누르면 브라우저 인쇄 창이 열린다.
화면용 다크 테마 대신 **흰 배경·검정 글자의 A4 문서**로 전환되며, 위험성 순으로
정렬된 구역별 평가 결과와 권고 대책이 표로 정리된다. 담당자·완료예정일 기입란과
결재란이 비어 있어 현장 확인 후 채워 넣어 그대로 사용할 수 있다.

- 별도 PDF 라이브러리를 쓰지 않는다. `@media print` CSS만으로 처리하므로
  의존성이 늘지 않고, 브라우저의 "대상: PDF로 저장"을 고르면 PDF가 된다.
- 등급 구분은 색상이 아니라 테두리 굵기로 한다. 흑백 인쇄를 고려한 선택이다.
- 구역 하나가 페이지 중간에서 잘리지 않도록 `break-inside: avoid`를 적용했다.

### 한계

- 신고 시각은 "사고 발생 시각"이 아니라 "신고를 누른 시각"이다. 시간대 분석을
  추가하려면 발생 시각을 별도로 입력받아야 정확해진다.
- 배후 요인이 태깅되지 않은 구역은 대책을 도출할 수 없다. 관리자의 태깅이 선행되어야
  한다는 점에서, 이 기능은 태깅 작업에 실질적 보상을 주는 장치이기도 하다.
- 가능성 산출이 신고 건수에 의존하므로, 신고 문화가 정착되지 않은 구역은 위험이
  과소평가될 수 있다. 앞서 언급한 "신고 편향" 문제와 같은 뿌리다.

## 관리자 접근 제어

대시보드에는 **누가 무엇을 신고했는지 실명과 사번이 표시**되고, 심각도·조치 상태를
변경할 수도 있습니다. 그래서 `/dashboard` 진입 시 암호를 요구합니다.

- 암호는 환경변수 `ADMIN_PASSWORD`로 지정합니다. 설정하지 않으면 기본값 `5432`가
  사용되므로, **실제 배포에서는 반드시 다른 값으로 바꿔야 합니다.**
- 암호 비교는 서버(`/api/admin/verify`)에서만 이루어집니다. 클라이언트 코드에 암호를
  넣으면 개발자 도구로 그대로 읽히기 때문입니다. `NEXT_PUBLIC_` 접두사를 붙이면
  브라우저로 전달되므로 절대 사용하지 마세요.
- 인증 상태는 `sessionStorage`에 저장됩니다. `localStorage`와 달리 **탭을 닫으면
  사라지므로**, 공용 PC에서 대시보드를 열어둔 채 자리를 떠도 다음 사람이 그대로
  이어받지 못합니다. 헤더의 "잠금" 버튼으로 즉시 잠글 수도 있습니다.
- 작업자 화면(`/`, `/report`, `/my-reports`)은 암호 없이 접근할 수 있습니다.
  여기까지 잠그면 신고 자체를 할 수 없기 때문입니다.

### ⚠️ 이것은 실제 인증이 아닙니다

**의도적으로 범위를 제한한 시연용 접근 제어입니다.** 화면 진입은 막지만,
`/api/reports` 같은 API는 여전히 공개되어 있어 주소를 아는 사람이 `curl` 등으로
직접 호출하면 데이터를 조회하거나 수정할 수 있습니다. 화면에 자물쇠를 달았을 뿐
뒷문은 열려 있는 셈입니다.

제대로 막으려면 **모든 API 라우트에서 서버 측 세션을 검사**해야 하고, 위조를 막기
위해 서명된 쿠키(또는 NextAuth 같은 라이브러리)가 필요합니다. 프로토타입 범위를
넘어선다고 판단해 넣지 않았으며, 실제 운영 배포 전에는 반드시 구현해야 합니다.

## 다국어 지원

한국 제조 현장은 외국인 근로자 비율이 높고, **언어 장벽 자체가 실제 사고 요인**으로
꼽힙니다. 신고 화면을 읽지 못하면 아무리 잘 만든 시스템도 쓰이지 않으므로,
작업자용 화면을 한국어 / English / Tiếng Việt 세 언어로 제공합니다.

- 화면 좌측 상단의 언어 전환 버튼으로 바꿀 수 있고, 선택은 브라우저에 기억됩니다
  (`lib/useLanguage.ts`).
- **음성 인식 언어도 함께 바뀝니다.** 영어를 고르면 `en-US`, 베트남어를 고르면 `vi-VN`으로
  인식하므로 모국어로 말해도 그대로 받아적힙니다 (`lib/i18n.ts`의 `SPEECH_LANG`).
- **공장 구역명도 번역**했습니다. 작업자가 자기 위치를 정확히 고를 수 있어야 신고 데이터의
  품질(특히 히트맵)이 유지되기 때문입니다.
- 번역 문구는 전부 `lib/i18n.ts` 한 파일에 모여 있습니다. 언어를 추가하려면 `Lang` 타입에
  코드를 넣고 사전 객체를 하나 더 작성하면 됩니다.

### 관리자 대시보드를 번역하지 않은 이유

의도적으로 한국어로 남겨두었습니다.

1. 다국어가 필요한 이유 자체가 "현장 작업자의 언어 장벽"이고, 안전관리자는 한국인입니다.
2. 인적 오류 분류(실수/망각/착오/위반)와 배후 요인은 **DB에 저장되는 값**입니다. 이걸
   화면 언어에 따라 바꾸면 데이터 일관성이 깨지고, 집계·필터가 언어별로 갈라집니다.

필요해진다면 `lib/i18n.ts`에 대시보드용 사전을 추가하고, 분류값은 지금처럼 저장값을
유지한 채 표시용 라벨 맵만 언어별로 두는 방식으로 확장할 수 있습니다.

## 배포하기 (Git + Render.com, 무료)

이 프로젝트는 Render.com의 무료 Web Service로 바로 배포할 수 있습니다.
Render는 (Vercel 같은 서버리스와 달리) 앱을 항상 켜져 있는 일반 서버 컨테이너로 실행하기
때문에, 로컬 파일 DB든 Turso 원격 DB든 그대로 동작합니다.

**데이터 보존에 대하여**: 무료 Web Service는 15분간 요청이 없으면 잠들고, 다시 깨어날 때
컨테이너가 새로 시작되어 내부 파일이 초기화됩니다. 두 가지 선택지가 있습니다.

- **그대로 두기(무료·데모용)**: 재시작마다 `ensureSeeded()`가 깨끗한 23건으로 자동
  채우므로 시연에는 문제없습니다. 다만 실제 접수된 신고는 사라집니다.
- **Turso 연결(무료·영구 보존)**: 위 4번처럼 환경변수 두 개만 설정하면 데이터가
  외부 DB에 남아 재시작과 무관하게 유지됩니다. 코드 수정은 필요 없습니다.

참고로 Render의 Persistent Disk는 유료 인스턴스($7/월~)에서만 붙일 수 있고,
Render 무료 Postgres는 **30일 후 만료·삭제**되므로 장기 보관에 적합하지 않습니다.

1. GitHub에 저장소 만들고 이 코드를 푸시합니다.
2. https://render.com 에서 GitHub로 로그인 → New + → Web Service → 방금 만든 저장소 선택.
3. 아래처럼 설정합니다.
   - Runtime: Node
   - Build Command: `npm install && npm run build`
   - Start Command: `npm run start`
   - Instance Type: Free
4. Environment 탭에서 환경변수를 추가합니다.
   - `ADMIN_PASSWORD` = 관리자 대시보드 암호 (설정하지 않으면 기본값 `5432`)
   - **(데이터 영구 보존을 원한다면)** `TURSO_DATABASE_URL` = `libsql://<db이름>-<조직>.turso.io`
   - **(위와 함께)** `TURSO_AUTH_TOKEN` = Turso에서 발급한 토큰

   설정하지 않으면 컨테이너 내부 파일에 저장되므로, 서비스가 잠들었다 깨어날 때
   데이터가 초기화됩니다(데모용으로는 무방).
5. Create Web Service를 누르면 빌드/배포가 시작되고, 끝나면 `https://<서비스이름>.onrender.com` 주소가 발급됩니다.
6. `https://.../report`에서 제출 → `https://.../dashboard`에서 "새로고침" 버튼을 누르면
   반영되는 걸 확인할 수 있습니다(자동 폴링은 30초 주기).

## 트러블슈팅

- **모든 파일에 빨간 줄이 그어지고 `JSX.IntrinsicElements` 오류가 뜬다면**: 이 저장소에는
  `node_modules`가 포함되어 있지 않아 편집기가 React/Next 타입을 찾지 못하는 것입니다.
  코드 문제가 아닙니다. `npm install` 후에도 남아 있으면 VS Code에서
  `Ctrl+Shift+P` → `TypeScript: Restart TS Server`를 실행하세요.
- **`npm install` 중 네이티브 모듈 빌드 오류가 난다면**: 네트워크가 제한된 환경에서
  Node 헤더 다운로드가 막혀 실패하는 경우가 있습니다. `npm install --ignore-scripts`로
  설치하면 이미 패키지에 포함된 사전 컴파일 바이너리를 사용해 정상 동작합니다.
- **마이크를 눌러도 아무 반응이 없거나 브라우저 탭 제목이 이상하게 보인다면**: `node_modules`와
  `.next` 폴더를 지우고 `npm install`부터 다시 실행해보세요. `app/layout.tsx`는 빌드 시
  Google Fonts(Barlow Condensed, Inter)를 인터넷에서 내려받으므로, 빌드 시점에 네트워크가
  불안정했다면 낡은 빌드 캐시가 남아있을 수 있습니다.
- **음성 인식이 계속 안 된다면**: 위 "음성 인식이 안 될 때 확인해야 할 것들" 섹션을 참고하세요
  (마이크 하드웨어 문제일 수도, 네트워크 차단 문제일 수도 있습니다).

## 알아두면 좋은 것들

- **왜 Prisma 같은 ORM 대신 SQL을 직접 썼나요?**: 프로토타입 단계에서는 별도 엔진
  다운로드나 마이그레이션 도구 없이 `npm install`만으로 바로 돌아가는 게 더 중요하다고
  판단했습니다. DB 로직은 전부 `lib/reportRepository.ts` 한 파일에 모여 있어서, 나중에
  Postgres로 옮기고 싶다면 이 파일의 함수 시그니처만 유지한 채 내부 구현을 교체하면 됩니다.
  실제로 v0.12에서 better-sqlite3 → libSQL 전환을 이 방식으로 처리했고, 컴포넌트는
  한 곳도 수정하지 않았습니다.
- **알려진 보안 이슈**: 현재 Next.js 14.2.x 라인에는 npm audit에서 보고되는 취약점이 일부
  남아있습니다(대부분 Next 16으로 메이저 업그레이드해야 완전히 해소됨). 로컬 프로토타입
  용도로는 문제없지만, 실제 서비스에 배포하기 전에는 `npm audit`을 확인하고 최신 안정 버전으로
  업그레이드하는 것을 권장합니다.
